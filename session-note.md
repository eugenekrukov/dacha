## Сессия 2026-09-01 — Единое серверное «отложено/удалено» для задач дня (4.7 закрыта): бэкенд + Android + веб

Закрыт баг-репорт «отложил задачу в приложении — на вебе она снова висит». Реализован план
`docs/archive/superpowers/plans/2026-06-27-unified-task-dismiss.md` целиком (миграция 054 лежала готовой
с 27.06, кода не было). Коммит `caf1dd8`, задеплоено в прод.

**Суть:** задачи дня — не строки в БД, а результат `buildTasks()`, поэтому снуз/удаление жило
только в `SharedPreferences` Android (снуз сгорал на завтра, удаление — никогда, и только на этом
устройстве). Теперь состояние в таблице `today_task_dismissals`, `GET /today` режет список один
раз на сервере — оба клиента получают одинаковую выдачу, синхронизация клиентам не нужна.

**Бэкенд** (`utils/todayLogic.js`, `routes/today.js`):
- `taskKey(t)` — новый экспорт, зеркало Kotlin `taskSnoozeKey`. Считается по **отформатированной**
  задаче: в `formatTasks` у `care_task_name` есть fallback на `product_example`, и именно эту
  строку клиент присылает обратно.
- Фильтрация в `GET /today`: `SELECT task_key ... WHERE target_date > CURRENT_DATE` → `Set`.
  Форматирование перенесено **до** среза `TASK_LIMIT` — иначе `tasks_total`/`tasks_hidden`
  считались бы до дисмиссалов и строка «Ещё задач: N» врала бы на отложенные.
- `POST /today/tasks/dismiss` → 204, upsert по `UNIQUE(user_id, task_key)`. `target_date` считает
  сервер: `snooze` → +1 день, `delete` → +`OVERDUE_WINDOW_DAYS` (21). 400 на невалидный `action`,
  пустой/длинный ключ и на `reminder:`-ключи (у напоминаний своя строка в `reminders` — вне скоупа v1).
- `GET /today/tasks/dismissed` → `{ task_keys: [] }`.
- Тесты: 5 новых в `__tests__/today.test.js` (фильтрация + пересчёт `tasks_total`, серверный
  `target_date` обоих действий, 400-валидация, 401, чтение).

**Android:**
- `TokenStorage`: `snoozeTask`/`getSnoozedTasksForToday`/`getSnoozedTasksForCalendar`/`deleteTask`/
  `getDeletedTasks`/`SnoozedCalendarTask` и два ключа prefs удалены как мёртвый код.
  `CalendarViewModel` — параметр `snoozedTasks` и ветка отрисовки отложенных на целевую дату тоже.
- `TodayViewModel`: `snoozeTask`/`deleteTask` → общий `dismissTask(key, action)` — оптимистично
  прячет карточку в `pendingHiddenTasks`, шлёт запрос, при ошибке возвращает карточку и
  перечитывает (online-only, в `ActionQueue` не кладём — как и прочие обычные действия).
  `pendingHiddenTasks` сбрасывается на успешном ответе сервера.
- **Отступление от спеки №1 (важное):** офлайн-закрытие задачи после залогированного действия
  (`loggedActionEvents`) раньше шло через локальный `snoozeTask` и работало без сети. Перевести
  его на API нельзя — офлайн запрос не уйдёт. Теперь оно прячет карточку через тот же
  `pendingHiddenTasks`, но **без** запроса; офлайн-фолбэк из кэша скрытие сохраняет (сбрасываем
  только на `Result.Success`).
- **Отступление №2:** спека предписывала `TodayViewModel` передавать в `attentionCount()`
  `emptySet()`. Это регрессия: care-просрочка на бейдже берётся из `Planting.overdueCareTask`
  (эндпоинт `/plantings`), мимо фильтра `GET /today` — с пустым набором отложенная care-задача
  продолжала бы зажигать бейдж. `loadToday` тянет `GET /today/tasks/dismissed` параллельно с
  остальными запросами; ошибка сети → пустой набор (бейдж максимум чуть завысит счётчик).
  `PlantingsViewModel` — по той же причине читает набор оттуда же вместо `TokenStorage`.
- Свайп отключён для карточек `reminder` (`SwipeActionsBox(enabled = ...)`) — сервер такие ключи
  не принимает, свайп просто возвращал бы карточку после перезагрузки.
- Тесты: 3 новых в `TodayViewModelTest` (скрытие + запрос, `action=delete`, откат при ошибке).

**Веб:** `taskKey()` в `api/schedule.ts`, `dismissTask()` в `api/client.ts`, на карточке задачи —
две иконки справа (часы «Отложить на завтра», крестик «Удалить») рядом с пилюлей просрочки;
у `reminder` их нет. Оптимистичное скрытие, при ошибке — `load()`. На кнопках `stopPropagation`
и для click, и для keydown, иначе Enter на кнопке заодно открывал бы лист записи действия.

**Побочно починен** давний рассинхрон: бейдж «требует внимания» учитывал снуз, но не удаление —
удалённая задача могла зажигать индикатор.

**Деплой:** `git reset --hard origin/main` + `pm2 restart dacha-api`; миграция 054 прогнана
через `sudo -u postgres psql -f` — **таблица уже существовала** (создавалась ранее общим
`npm run migrate`), владелец `dacha_user`, GRANT не потребовался. Веб пересобран на VPS в
`/var/www/dacha-web`.

**Проверка на проде** (demo@dacha.ru, участок 12): `GET /today` отдавал 9 задач → `dismiss`
сгруппированной «Прополки» вернул 204 → в следующей выдаче её нет, `tasks_total` 8,
`GET /today/tasks/dismissed` вернул ключ, `reminder:`-ключ отбивается 400. Тестовая строка из БД
удалена, чтобы демо-аккаунт (он же для ревьюера Google Play) остался чистым.

**Гочи по тестам:** полный `npm test` бэкенда даёт 4 плавающих падения
(`auth`/`push-tokens`/`reminders`) — в изоляции те же файлы зелёные, это таймауты под нагрузкой
полного прогона. Отдельно и стабильно падает `telegramQueue.test.js` («vk_post_url пуст →
continueUrl = фолбэк») — воспроизводится и в изоляции, к этой сессии отношения не имеет,
**осталось незакрытым**.

**Вне скоупа v1 (как в спеке):** снуз/удаление reminder-карточек, офлайн-очередь для свайпов
(`ActionQueue`), показ отложенных задач в календаре на их целевую дату, миграция старых локальных
записей Android на сервер, чистка устаревших строк `today_task_dismissals`.

## Сессия 2026-08-19 (3) — баг: полив из карточки не закрывал групповую задачу «Полить» на Android (офлайн)

Триггер: «Если у посадки подошёл срок полива, и полить посадку из карточки, то необходимость
полива не исчезает из заданий дня».

**Диагностика:** проверил весь путь — backend (`utils/todayLogic.js` → `GET /today`) и веб
подтверждены живым тестом (демо-аккаунт, планировка Редис/Огурец, посадка через API и через UI
карточки): и одиночная, и групповая задача «Полить: X, Y и ещё N» корректно схлопываются после
записи полива, вплоть до полного исчезновения при закрытии последней посадки в группе. Баг — только
на **Android, в офлайн-сценарии**.

**Root cause:** `TodayViewModel.kt`, коллектор `actionsRepository.loggedActionEvents` — при офлайн
записи действия локально «снузил» подходящую задачу по `it.plantingId == info.plantingId`. Для
ГРУППОВЫХ задач (полив/подкормка нескольких посадок с одинаковым сроком) сервер отдаёт
`planting_id: null`, а id посадок лежат в `planting_ids` — сравнение никогда не совпадало, задача
не снузилась и висела в «Сегодня» до следующего онлайн-обновления. Онлайн баг не проявлялся, потому
что следом всегда шёл `loadToday(silent=true)`, который перечитывает с сервера и там всё верно;
офлайн же `loadToday` падает на `TodayCache` — старый снимок без снуза, куда полив не попал.
Заодно нашёл соседнюю недостающую проверку: снуз не сверял ТИП действия с типом задачи (полив
на грядке с одновременной подкормкой снял бы не ту карточку) — у `PlantingsViewModel.onActionLogged`
такая проверка уже была, в `TodayViewModel` её не было.

**Фикс** (`android/.../ui/today/TodayViewModel.kt`): новая функция `taskClosedBy(task, info)` —
сверяет посадку (одиночный `plantingId` ИЛИ вхождение в `plantingIds`) И тип действия против типа
задачи (маппинг `watering_due→watering`, `fertilizing_due→fertilizing`,
`transplant_due→transplanting`, `care_task_due→careTaskActionType(...)`, зеркалит
`PlantingsViewModel.onActionLogged`). Коллектор теперь фильтрует ею вместо голого сравнения
`plantingId`.

**Тесты:** 5 новых юнит-тестов `taskClosedBy` в `TodayViewModelTest.kt` (закрывает групповую задачу
поливом одной посадки · не закрывает для чужой посадки · не закрывает действием другого типа ·
закрывает одиночную задачу · закрывает `care_task_due` по типу действия). Полный прогон обоих
флейворов (`:app:testGplayDebugUnitTest :app:testRustoreDebugUnitTest --offline`) — зелёный,

единой команды «перегенерировать всё» (генератор per-файл, состояние в `.blog-manifest.json` на
VPS, не в git) — правка шапки требовала либо перегенерации сотен файлов, либо была вообще
невозможна для части постов (исходники `filtered-part1-aug.md`/`filtered-part2-jul.md` уже не
существуют на сервере).

**Решение — nginx SSI:**
- `landing/_includes/header.html` и `footer.html` — общие для всего сайта (`<!--#include virtual="..." -->`,
  `ssi on;` в `/etc/nginx/sites-available/dacha`). Правка меню/кнопки входа/подвала = правка двух
  файлов, без перегенерации существующих страниц.
- `seoPage.js`: `renderShell` больше не инлайнит шапку/подвал — только SSI-инклюды.
- `index.html`: убрана собственная копия шапки (включая анимированный SVG-лого — ради
  единообразия теперь везде простое 🌻) и подвала (более богатый вариант, со ссылками на
  сторы/соцсети, стал общим). Поправлен scrollspy под новый формат href (`/#id` вместо `#id`).
- `generate-blog.js`: добавлен флаг `--refresh-existing` — перегенерирует только уже
  опубликованные посты (по совпадению title в манифесте), не публикует остальные статьи файла.
  Понадобился, потому что `batch-2026-07-part2.md`/`batch-2026-08-part1.md` успели накопить
  статьи, которых в блоге ещё нет — прогон без фильтра выложил бы их как побочный эффект простого
  обновления обёртки.
- Фикс переноса шапки на 3 строки (справочник/блог): общий `.wrap` — 900px (под текст статьи), а
  для шапки на главной было отдельное `header .wrap{max-width:1160px}` — не было перенесено в общий
  `style.css`. Плюс `.nav{flex-wrap:wrap}` разрешал перенос вместо однострочного сжатия.

**Накладки по дороге (обе замечены до реальных последствий):**
- Первая попытка правки nginx-конфига через `sed` с многострочной вставкой по SSH сломала файл на

  положил исходную папку **внутрь** неё (`assets/assets/`), старый `style.css` снаружи остался

## Сессия 2026-08-09 — F2: AI-диагностика по фото, от прототипа до прода

Заход через реальный вопрос: в статьях для Дзен советовали вести учёт болезней в дневнике —
дневник это и правда умеет (тип действия «Другое»/«Заметки» + текст), но неочевидно. Чинили
discoverability (подсказки, кликабельное расписание, переименование «Другое»→«Заметки» — эта
часть осталась на отдельной, ещё не смерженной ветке `feat/action-log-diary-hints`), и по ходу
всплыла бо́льшая идея: раз в Tender AI уже есть дешёвый LLM-слой (Qwen), можно почти бесплатно
сделать AI-диагностику по фото для платной версии — F2 из мастер-плана, до этого просто «research».

**Прототип (до кода):** прогнал реальный ключ Qwen на трёх выборках. Open-set (модель сама
называет диагноз из всей номенклатуры) — 20% точности. Closed-set (кандидаты только из
`guide_entries` сфотографированной культуры) — 80-94% на разных типах фото. Разница огромная →
архитектурное решение: только closed-set, никогда открытый вопрос. Записано в память
`project_dacha_ai_diagnosis.md`.

**Реализация (subagent-driven, изолированный worktree):** 8 задач плана `docs/archive/superpowers/
plans/2026-08-09-ai-diagnosis-f2.md` — миграция `066`, `aiDiagnosisService.js` (Qwen-VL,
OpenAI-совместимый endpoint, паттерн зеркалит Tender), `POST /photos/:id/diagnose` под платным
гейтом, веб- и Android-UI. Каждая задача — независимый implementer-агент + spec-review +
code-quality-review, с реальными фиксами по пути (утечка пути ФС в 500-ошибке, гонка `viewer`
при асинхронном ответе).

**Живая проверка вскрыла три реальных бага, которых не было в плане:**
1. Кнопка «Определить» была видна только в дневнике фото — неказуально. Добавлен прямой вход
   с вкладок «Болезни»/«Вредители» на обеих платформах (снял фото → сразу диагноз).
2. Просмотр фото открывался в натуральную величину без скролла (веб) — классический баг
   флексбокса (`flex-1` без `min-h-0`). Заодно нашёлся **второй независимый просмотрщик фото**
   (лента «Мой участок», `ProfileScreen.tsx`) с тем же багом и без кнопки диагностики вовсе.
3. На Android кнопка пряталась под системной навигацией — задокументированный в самом файле
   баг Compose `Dialog` (системные инсеты не доходят до композиции). Настоящий фикс —
   `WindowCompat.setDecorFitsSystemWindows(window, false)`, а не отступ на глаз.

**Ещё одна находка при ручной проверке (не баг кода, баг продукта):** у многих культур в
справочнике всего 1-2 болезни/вредителя — фиксированный «топ-2-3» на таком списке = 100%
справочника культуры, выглядит как обман, а не диагноз. Правило: показываем строго МЕНЬШЕ
полного списка кандидатов (1→1, 2→1, 3-4→2, 5+→3), кроме случая с единственным кандидатом —
там отбирать не из чего, это честный единственный ответ.

**Статус на конец сессии:** бэкенд и веб задеплоены в прод (`8ca74b2`), проверено live-смоук-тестом
с реальным фото фитофтороза. Android код готов и компилируется, релиз ещё не собирался.

## Сессия 2026-08-03 — задачи дня: погода перестала врать

Вопрос владельца был узкий: «отмена полива при дожде есть, а увеличение при жаре?». Увеличения
не было — `heat_risk` собирался, но на интервал полива не влиял вообще. Разбор списка задач
целиком вскрыл, что до новых фич надо чинить точность существующих.

**Что врало.**
- **Две противоположные формулы теплицы.** `todayLogic.wateringIntervalDays` — ×0.8 (чаще),
  `recommendations.js` — своя `ceil(freq × 1.3)` (реже). Один участок жил по взаимоисключающим
  правилам в задачах и в советах. `recommendations.js` теперь зовёт общую функцию.
- **Дождь отменял полив в теплице** — условие `!rainExpected` применялось ко всем посадкам.
- **Прошедший дождь не учитывался вообще.** После 20 мм ливня карточка продолжала требовать
  «полить, 5 дн. без воды»: `precip_mm` жил только в тексте совета. Теперь последний настоящий
  дождь (≥5 мм) засчитывается как полив — берём `MAX(fetched_at)` из уже копящихся снимков,
  новой таблицы не понадобилось.
- **«Дождь» = одна вероятность.** 70% на 0.2 мм мороси отменяли полив. Теперь нужны И
  вероятность ≥70%, И объём ≥3 мм (из `forecast_json`).
- **Решение на сегодня принималось по завтрашнему прогнозу** (`weatherService` клал в
  `precip_prob_pct` вероятность за индекс 1). Поле стало сегодняшним — это чинит и карточку
  погоды; завтрашний день берётся из `forecast_json[1]`.
- **Сортировка врала о срочности.** Жёсткий приоритет типа ставил care-задачу «через 3 дня»
  выше полива, забытого на неделю. Введена `urgency()`: приоритет минус просрочка (потолок 3 дня),
  ещё не наступившие задачи всегда ниже наступивших (кроме заморозков).
- **Жара глушила все советы** — `break` в цикле по посадкам в `recommendations.js` обрывал
  выдачу на первой итерации, участок терял `harvest_soon` и `stage_tip`. Советы «на участок»
  вынесены из цикла.
- **`tasks_total` считался ПОСЛЕ среза** и не мог быть больше 7. Срез переехал в `routes/today.js`,
  добавлен `tasks_hidden` → строка «Ещё задач: N» на веб- и Android-экране.

### Веб: CSP молча блокировала каждое фото в приложении (`54d84df`, задеплоено)

Владелец проверил семена в вебе: фото не подтягивается, редактура не работает. Консоль дала
ключ сразу — `Loading the image 'blob:…' violates CSP directive "img-src 'self' data: …"`.

**Масштаб больше, чем выглядел.** `AuthImage` тянет приватные фото (`X-Accel-Redirect` по Bearer)
через `fetch` + `URL.createObjectURL`, потому что обычный `<img src>` не отправит токен. Все такие
картинки — `blob:`-URL, а его в `img-src` не было. То есть ломались **не семена, а вообще все фото
в веб-версии**: лента «Мой участок», фотодневник посадки, карточки действий. Просто до семян
никто не смотрел на это свежим взглядом.

**Почему не поймали раньше:** в `vite.config.ts` есть плагин `strip-csp-meta-in-dev`, снимающий
мету в dev (иначе HMR-сокет и стили ломаются). Локально фото грузились всегда — дефект жил только
в проде. Проверять CSP-вещи имеет смысл на прод-сборке, `npm run build` + просмотр `dist/index.html`.

Заодно разрешён `wss://mc.yandex.*` в `connect-src`: вебвизор Метрики включён (`webvisor:true`)
и на каждой загрузке стучался в заблокированный сокет. Пиксель `yandex.ru/an/mapuid` **намеренно
оставлен заблокированным** — это синхронизация рекламных аудиторий, рекламы в продукте нет,
расширять доверие незачем.

**Редактура.** Оказалось, её просто не было: `PATCH /seeds/:id` с самого начала принимал
`crop_name` и `variety`, но в вебе единственным изменяемым полем было «годен до» — маленький
инлайн-input в карточке. Добавлена модалка правки на общем компоненте `Modal` (фокус-ловушка,
Escape), инлайн-поле убрано как дубль. Плюс просмотр фото по клику — паритет с Android
(`photo_url`, не превью).

Проверено: `tsc --noEmit` чист, прод-сборка содержит нужный CSP, живой `/app/` отдаёт
`img-src … blob:`. Тем же заходом выложен лендинг с «55 культур» (7 вхождений, «45+» не осталось).

⚠️ **Все четыре правки должны попасть в vc11 до публикации** — иначе «Мои семена» уедут
в магазины ровно с теми дефектами, которые владелец нашёл руками. Требуется пересборка AAB.

## Сессия 2026-07-30 — советы дня врали про культуру (`STAGE_TIPS`)

Владелец прислал скриншот «Сегодня»: под заголовком **Укроп** — совет про трескающиеся
**корнеплоды**, под **Горохом** — «окучьте картофель и капусту». Симптом выглядел как
перепутанная привязка совета к посадке, но привязка исправна.

**Корень.** `STAGE_TIPS` (`backend/src/data/tips.js`) — пул, общий для всех культур, выбор идёт
только по стадии; а `routes/recommendations.js` отдаёт совет вместе с `crop_name`, и клиент
рисует его заголовком карточки. Значит любой текст, называющий конкретную культуру или тип
органа, автоматически становится ложным для всех остальных культур в той же стадии. Два
совета в `growing` были написаны как культуро-специфичные — этого достаточно.

Тот же класс бага чинили 2026-07-28 (`potOnly` — советы про подоконник на грядочных посадках):
там ограничение выражалось признаком посадки, здесь ограничения быть не должно вовсе — пул
обязан состоять из формулировок, годных любой культуре.

**Замысел был культуро-специфичный** (уточнение владельца) — и данные для этого давно лежат
в `crops` (миграции 005/006/038): `watering_details.notes` («Умеренный полив. При засухе быстро
идёт в стрелку» — это ровно про укроп), `fertilizing_schedule`, размеченный **по стадиям**,
`diseases[].prevention`, `pests[].signs`. Их никто не подключал: `recommendations.js` даже
делал `SELECT c.fertilizing_schedule` и выбрасывал результат. Поэтому фикс — двухслойный.

**Слой 1 — культуро-специфичный (главный).** `getCropStageTip(crop, stage, …)` собирает пул
советов из уже имеющихся JSONB-полей культуры и ротирует его тем же индексом
(день месяца + `planting_id`). Стадии подкормок маппятся на стадии посадки
(`harvesting`→`fruiting`, `sowing`/`sprouted`→`seedling`); болезни и вредители показываются
только с `growing` — до всходов осматривать нечего. Новой таблицы советов не заводили.
В роут добавлены недостающие поля выборки, приоритет: сначала совет про культуру, и только
при её отсутствии в данных — общий.

**Слой 2 — общий пул как фолбэк.** Агрономия заполнена у **32 культур из 55** (006 — овощи,
зелень, ягоды; 038 — кусты и деревья). У остальных, включая **Горох** со скриншота, советов
про культуру нет, и они получают `STAGE_TIPS`. Раз этот пул показывается под именем культуры,
его тексты обязаны подходить любой — поэтому нарушители в нём всё равно переписаны:
`growing` — про полив и про рыхление после дождя; `flowering` — «потряхивайте томаты и перцы»
→ про проветривание теплицы; `harvesting` — «плоды набрали сахар», «плоды упругие»,
«перезревшие плоды на кусте» → без указания органа. Над `STAGE_TIPS` — комментарий с правилом
и ссылкой на страж.

**Тесты:** 461/461 (было 455). Страж на нейтральность общего пула (все стадии × методы
посадки × 24 id через регексп имён культур и слов «корнеплод/куст») + 5 тестов на новый слой:
культура с данными отдаёт свой совет, культура без данных → `null` (откат на общий пул),
подкормка берётся строго для текущей стадии, болезни не показываются до всходов, прямой посев
до всходов молчит.

**Задеплоено и проверено на живом проде** (`f6ab5d8`, `pm2 restart`, health 200). `GET

## Сессия 2026-07-29 (2) — инвентарь семян «Мои семена» (backend + web + Android)

Фича из бэклога (`docs/ux-roadmap.md`, идея с разбора easyDacha) реализована на всех трёх
платформах. Запрошенный объём: культура, сорт, фото пакетика, проверка срока годности.
**OCR пакетика владелец решил не тащить в первую версию** — сначала посмотреть, пользуются ли
инвентарём вообще (варианты и их цена записаны в roadmap, чтобы не пересчитывать заново).

**Решения по данным:**
- Культура — свободный текст, а не FK на `crops`: в справочнике 55 позиций (овощи, зелень, ягоды,
  кусты), а в коробке лежат ещё и цветы. В вебе ввод подсказывается нативным `<datalist>` из
  справочника, но не ограничивается им. Плата за это — список покупок (следующий шаг фичи)
  потребует связи с `crops`; отмечено в roadmap.
- Срок годности хранится `DATE`, но с пакетика читается месяцем («годен до 12.2027»). Месяц
  нормализует бэкенд (`normalizeExpiry`: `2027-12` → `2027-12-31`, високосный год учтён), чтобы
  правило жило в одном месте, а не в двух клиентах. Пустая строка = снять срок — это же поведение
  использует Android, т.к. Moshi не сериализует `null`-поля и «снять» иначе не выразить.
- Флаги `expired` / `expires_this_year` считает SQL в `SELECT`. Клиенты только раскрашивают:
  красный «Просрочен», оранжевый «Использовать в этом сезоне». Просроченные — вверху списка.
- Фото: одно на пакетик, отдельным multipart-эндпоинтом `POST /seeds/:id/photo` (у нового пакетика
  id появляется только после создания). Файлы — в `seeds/<userId>/`, через тот же `imageService`
  (добавлен параметр `dir`, дефолт прежний). `photoSweepJob` сканирует только `plantings/`,
  так что чужие каталоги он не тронет.

**Ограничения и что не делалось:** гейта подписки нет (фича бесплатная), стоит только потолок
200 пакетиков на аккаунт — фото занимают диск. Количество пакетиков и отметка «посеяно» не
заводились: в запросе их не было, а удаление закрывает сценарий «семена кончились».

**Проверка.** Бэкенд — 455/455 (`seeds.test.js`, +18: нормализация месяца, потолок, PATCH-семантика

⚠️ На проде заработает только после деплоя бэкенда; до тех пор поведение прежнее, без регрессии.

## Сессия 2026-07-05 — Web: фикс разлогина при сетевой ошибке на старте (AuthContext)

**Баг**: при старте SPA `AuthContext` тянет `api.me()`, и `.catch(() => tokenStore.clearAll())`
стирал `dacha_token` при **любой** ошибке — включая сетевые сбои и 5xx. Пользователь с валидным
токеном разлогинивался после одной неудачной загрузки (наблюдалось вживую в локальном превью).

**Фикс** (`web/src/auth/AuthContext.tsx`): токен чистится только при `ApiError` со статусом
401/403 (явный отказ бэкенда); при сетевой ошибке / 5xx токен остаётся, приложение тихо
продолжает без профиля — он подтянется при следующей загрузке. 401 в `request()` (api/client.ts)
и так чистит токен сам — ветка в catch оставлена явной для 403 и читаемости.

**Верификация** (dev-превью, Vite-прокси):
- прокси на мёртвый порт (`VITE_API_TARGET=http://127.0.0.1:59999`) + валидный по форме токен →
  `/auth/me` = 500 → после перезагрузки `dacha_token` **на месте** ✅
- прокси на прод + протухший токен → `/auth/me` = 401 → токен стёрт, показан логин ✅
- `npx tsc --noEmit` — чисто; impact-анализ GitNexus: LOW (единственный потребитель — `main.tsx`).

  идентификаторы не собираются» — CSP тут **случайно делает ровно то, что нужно** (блокирует). По
  решению владельца — **оставлено как есть**, CSP не трогали ни в какую сторону.

**Инфраструктура Obsidian-базы — найден и починен структурный баг** (владелец попросил проверить
актуальность базы, особенно «08 Статус и бэклог»):
- Заметка «08» была устаревшей (заголовок «2026-07-01», не отражала ничего из работы над
  `/spravochnik/`) — актуализирована.
- **Более серьёзная находка**: `Корень репозитория/*` в Obsidian задуманы как hardlink на файлы
  репо (`12 Полный репозиторий (зеркало).md`), но `fsutil hardlink list` показал, что 3 из 11
  (`summary.md`, `session-note.md`, `CONVENTIONS-backend.md` — ровно те, что недавно правились)
  реально разорваны. Причина: `git pull`/редакторы перезаписывают файл через temp-file+rename —
  это создаёт новый inode по тому же пути, вторая ссылка остаётся на старом иноде со старым
  содержимым, без единой ошибки. Junction (`Документация/`, `Дизайн-система/`) этой проблеме не
  подвержен (резолвит путь к папке каждый раз, а не держится за inode файла).
- Временный фикс — пересоздал как hardlink заново (без прав администратора это единственный
  доступный вариант на тот момент).
- Владелец нашёл и включил Developer Mode (Windows 11: Параметры → Система → Для разработчиков,
  не там, где я изначально предполагал), перезагрузил компьютер.
- **Финальный фикс**: все 11 ссылок пересозданы как **symlink** — переживает rename-перезапись,
  разрыв больше не должен повторяться. Сделано безопасно: сначала symlink под временным именем,
  проверка содержимого чтением байт (не через `Length` — на symlink та возвращает 0, это не признак
  поломки), и только потом замена оригинала. По пути — реальный баг: `New-Item -ItemType
  SymbolicLink` в Windows PowerShell 5.1 не работает без прав администратора даже при включённом
  Developer Mode (известное ограничение версии, не использует API-флаг «непривилегированного»
  создания symlink); помогает `cmd /c mklink` напрямую. Всё задокументировано в заметке «12».
  ⚠️ Один неудачный первый заход: цикл удалял оригинал ДО проверки успеха создания symlink — на
  секунду все 11 файлов в Obsidian оказались удалены (репозиторий не пострадал, трогались только
  копии-ссылки в Obsidian). Восстановлено немедленно через hardlink, затем сделано заново безопасно.

## Сессия 2026-06-21 — F1 офлайн «Сегодня»: read-кэш + очередь записи (Android + backend)

Полный цикл superpowers по фиче **F1 (офлайн-режим «Сегодня»)** через subagent-driven (12 задач,
TDD/ревью на задачу): брейнсторминг → спек (`docs/superpowers/specs/2026-06-21-offline-today-design.md`)
→ план (`docs/superpowers/plans/2026-06-21-offline-today.md`) → реализация. **НЕ задеплоено** (ветка
`feature/offline-today`, не влита). Веб вне scope (полевой сценарий — Android).

**Что закрывает:** инсайт №1 (дача без связи) — экран «Сегодня» был завязан на API, при сетевой ошибке
уходил в `Error` (кэша не было). Теперь: офлайн-чтение из кэша + баннер; запись действий (лог/смена
стадии/удаление) офлайн ставится в очередь и синхронизируется при возврате связи.

**Backend (миграция 045, тесты 330 vitest, +3):** `action_logs.client_id UUID` (nullable) + частичный
UNIQUE-индекс; `POST /actions` принимает опц. `client_id` (ключ идемпотентности, UUID-валидация→400) и
`logged_at` (клиентское время, `COALESCE($5,NOW())`); атомарный `ON CONFLICT (client_id) DO UPDATE …
RETURNING` (по ревью — вместо DO NOTHING+SELECT, без гонки на двойной отправке). IDOR-проверка раньше
валидации. Старые клиенты без `client_id` работают по-прежнему. Стадия «Высадки» — через существующий
`PATCH /plantings/:id/stage` (idempotent), бэкенд не трогали.

**Android (подход A — без Room/WorkManager):**
- `data/local/TodayCache.kt` — снимок «Сегодня» (Moshi→SharedPreferences `dacha_today_cache`),
  привязан к `gardenId`; `save/load/updateActions/clear`.
- `data/local/ActionQueue.kt` — персистентная FIFO-очередь `QueuedOp` (LOG/STAGE/DELETE), `@Synchronized`,
  мягкий потолок 200, реактивный `size: StateFlow`.
- `data/sync/ActionSyncManager.kt` — прогон очереди под `Mutex.tryLock()`: успех/4xx(вкл.404 DELETE)/
  конфликт `client_id` → снять; 5xx/IOException → стоп до след. триггера.
- `data/sync/ConnectivityObserver.kt` — `registerDefaultNetworkCallback`, `onAvailable`→`sync()`; старт
  из `App.onCreate`. +`ACCESS_NETWORK_STATE` в манифесте.
- `Result.Error.isNetwork` (IOException vs HttpException) — отделяет офлайн от прикладных ошибок.
- `ActionsRepository` — онлайн шлёт сразу (с `client_id`+`logged_at`); офлайн (IOException) → enqueue +
  оптимистичный синтетический `ActionLog` (отриц. id, `pending=true`) в кэш-ленту; `changeStage`
  (офлайн→STAGE в очередь); `deleteAction(id, clientId?)` (несинхронизированное — выкинуть из очереди без
  сервера; серверное офлайн → DELETE в очередь). Событие `loggedActionEvents`.
- `TodayViewModel` — кэш сохраняется при успехе + `syncManager.sync()`; при **сетевой** ошибке с кэшем →
  `Success(offline=true, cachedAt)` (иначе `Error`); по `loggedActionEvents` оптимистично закрывает
  задачи посадки (snooze, обратимо) + silent reload. `queueSize` проброшен в UI.
- UI (`TodayScreen`): баннер «Нет связи · данные от HH:MM · N в очереди» (рус. плюрализация), пометка
  «↑ ждёт отправки» на pending-действиях.
- Logout чистит `TodayCache`+`ActionQueue` (как push-токен) — чужие данные не показываем/не шлём.

⚠️ **Android JVM unit-тесты в этом окружении НЕ запускаются** — `ClassNotFoundException` тест-воркера для
ВСЕХ классов (вкл. пред-существующие), корень — **кириллический путь** `Календарь дачника` (это и есть

## Фикс 2026-06-13 — пуш по чужому участку при смене аккаунта на устройстве

**Симптом**: на `e-krukov@yandex.ru` пришёл пуш «💧 Полейте: Томат», хотя на этой учётке Томат не
посажен.

**Причина**: `push_tokens` имеет `UNIQUE(user_id, token)`, поэтому один физический FCM-токен может
быть зарегистрирован сразу за несколькими пользователями. На тестовом устройстве (Samsung A55)
сначала был залогинен `e-krukov@ya.ru` (`user_id=2`, есть просроченный полив Томата на участке `id=3`),
потом на том же устройстве залогинились как `e-krukov@yandex.ru` (`user_id=6`) — старая привязка
токена к `user_id=2` не удалилась. `careRemindersJob` нашёл просрочку у `user_id=2`,
`getTokensForGarden` вернул тот же физический токен (привязанный к `user_id=2`) → пуш ушёл на
устройство, где сейчас открыт другой аккаунт.

**Фикс** (`28e029e`, влит в `main`, задеплоен): `POST /push-tokens` перед upsert удаляет регистрацию
этого токена у ВСЕХ остальных `user_id` — токен принадлежит одному физическому устройству, поэтому
закрепляется только за текущим залогиненным аккаунтом. Тест `push-tokens.test.js` (5 тестов, +1
маршрут зарегистрирован в `helpers/buildApp.js`). На проде вручную удалена зависшая строка
`push_tokens.id=155` (`user_id=2`, тот же токен).

**Фикс 2** (`4f1e7aa`, влит в `main`, push-only — production-код не менялся): тест
`careRemindersJob.test.js` «подкормка: есть расписание и >14 дней без подкормки» падал (pre-existing,
не связано с фиксом выше): фикстура `fertilizing_schedule: [{ day: 14 }]` не содержит поля `stage`,
которое ищет `schedule.find(f => f.stage === fertStage)` в `careRemindersJob.js`/`todayLogic.js` —
`fertEntry` всегда был `undefined`. Реальные данные `crops.fertilizing_schedule` (миграция 006) всегда
содержат `stage` (например `{"stage":"growing", ...}`) — производственный код корректен, фикстуру
