## 2.3. «Работы на этой неделе в вашем регионе»

### Проблема
С осени у большинства посадки закрыты, «Сегодня» пустеет, и открывать приложение незачем.
Что уже есть: `GET /recommendations` отдаёт плоский список «Советов». В нём **один** совет месяца
(`SEASONAL_TIPS`, 3 фразы на месяц, одинаковые для всех зон), окна посева из `crops.sowing_*`
(только весна) и лунный совет. Осенних и зимних работ по региону нет.

### Что видит пользователь
Блок на «Сегодня» сразу под погодой: **«На этой неделе · {регион}»**, 3–5 пунктов. Показывается
всегда: и без посадок, и у гостя (2.1).

```
На этой неделе · Московская обл.
 ✂  Обрезать малину после плодоношения            у вас есть
 🧄  Посадить озимый чеснок: окно до 10 октября     → статья
 🍂  Собрать листья в компост, больные — сжечь
 [Показать ещё 3]
```

- Пункт: иконка категории, заголовок, одна строка деталей (раскрывается по тапу), метка
  **«у вас есть»**, если культура из пункта есть в активных посадках (такие пункты идут первыми).
  Если есть статья в справочнике или блоге, то ссылка «→ статья».
- Действия у пункта: **«Сделано»** и **«Не актуально»**. Пункт скрывается до следующего сезона.
  Хранится локально (как сейчас скрытие рекомендаций): ключ `{work_id}:{год}`. «Сделано» в журнал
  не пишется, потому что посадки нет.
- Зимой (дек–фев) блок не пустеет: планирование, заказ семян, снегозадержание, проверка
  хранилища; с конца января — посев рассады.

### Откуда данные
1. **Новый файл контента `backend/src/data/seasonalWorks.js`**, по образцу `tips.js`. Без таблицы
   и миграции: контент правится коммитом.
   ```js
   { id: 'raspberry-cut-after-harvest', title, details, category: 'prune'|'sow'|'plant'|'harvest'|'care'|'prep'|'plan',
     window: { from: 245, to: 275 },   // день года для зоны 4 (база)
     anchor: 'fixed' | 'autumn' | 'spring',
     crop: 'Малина' | null,            // для метки «у вас есть»; сверяется по crops.name
     link: '/spravochnik/…' | '/blog/…' | null }
   ```
   Объём: **~80–100 работ на весь год**. Контент пишу я по агрономическим срокам, вы вычитываете.
2. **Сдвиг по зоне**: существующий `getZoneDayOffset(zone)` (±10 дн. на зону, `tips.js`).
3. **Осенние работы** (`anchor: 'autumn'`) привязаны к фактическому осеннему переходу участка через +5 °C
   (`storedSeasonEnd`, `seasonService.js`), если он уже посчитан. Иначе к норме зоны.
   Весенние (`anchor: 'spring'`) — так же, к `storedSeasonStart`.
4. **Окна посева** из `crops.sowing_start_day/sowing_end_day` (сейчас это `sowing_*` в
   `/recommendations`) переезжают в этот блок как категория `sow`.

### API
`GET /season-works?garden_id=` (auth, гость тоже) → `{ region, week_start, items: [{ id, title, details,
category, crop, in_garden, link, window_end }] }`. Отбор: окно работы пересекается с [сегодня; +7 дн.],
сортировка: «у вас есть» → заканчивается раньше → остальное. Отдаём до 8 пунктов, клиент показывает 3 + «ещё».

`/recommendations` не трогаем: старые клиенты (vc17) продолжают получать его как раньше. Новые
клиенты отфильтровывают из него `seasonal_tip`, `sowing_season` и `sowing_soon`, чтобы не было дублей.

### Где правим
- Бэкенд: `data/seasonalWorks.js`, `routes/season-works.js`, регистрация в `app.js`.
- Android: `TodayScreen.kt` (блок), `TodayViewModel.kt` (+ запрос), `TodayCache` (офлайн), `DachaApi`.
- Веб: `TodayScreen.tsx`, `api/client.ts`, `api/types.ts`.

### Проверка
- vitest: **покрытие** — для каждой зоны 3–6 и каждой недели года ≥ 3 работы; сдвиг по зоне;
  осенний якорь от `storedSeasonEnd`; метка `in_garden`.
- Руками: демо-участок (Краснодар, зона 6) и участок зоны 3; дата подменяется параметром в тесте.

## 2.1. Гостевой режим

### Проблема
По стратегии ~60% установивших теряются до регистрации. Сейчас путь такой: Intro → **Login/Register** → участок →
культуры → «Сегодня». С сегодняшнего дня статьи блога ведут на `/app/`, и там тоже сразу стена логина.

### Решение: гость — обычный пользователь без email
Не «локальный режим с переносом данных», а **анонимная серверная учётка**. Все эндпоинты,
офлайн-кэш и синхронизация работают без изменений. При регистрации та же строка `users`
получает email и пароль, поэтому **переносить данные не нужно**.

### Бэкенд
- **Миграция 092**: `users.email` и `users.password_hash` → `DROP NOT NULL`;
  `+ is_guest BOOLEAN NOT NULL DEFAULT false`, `+ guest_device_id TEXT UNIQUE`.
- `POST /auth/guest` `{ device_id, store, install_referrer }` → `{ token, user }`. Идемпотентен по
  `device_id`: повторный вызов возвращает того же гостя. `device_id` — случайный UUID, сгенерированный
  клиентом и сохранённый в prefs/localStorage (не `ANDROID_ID`). Rate limit как у `/register`.
- Токен гостя живёт те же 30 дней. На 401 клиент гостя молча повторяет `/auth/guest` с тем же `device_id`.
- `POST /auth/guest/claim` (auth) `{ email, password }` → email/пароль в ту же строку, `is_guest=false`,
  код подтверждения как при `/register`. Возвращает новый токен. Email занят → 409 (см. вопрос 2).
- **Что гостю закрыто** (403 `{ error: 'account_required' }`, клиент ведёт на регистрацию):
  оплата (`yookassaService` строит чек по `user.email`, для НПД-чека email обязателен), промокод,
  смена пароля/email. Лимит бесплатного тарифа — тот же (3 посадки / 1 сад).
- Письма: гостю ничего не уходит (email нет). Джобы уже выбирают по `email_verified`, это
  проверю тестом.
- `/me` отдаёт `is_guest`. Скилл `/statistic_user` показывает гостей отдельной строкой.

### Android
- Intro, последний экран: главная кнопка **«Начать»** → тихий `/auth/guest` → CreateGarden (регион) →
  OnboardingCrops → «Сегодня». Под ней ссылка «Уже есть аккаунт? Войти».
- `TokenStorage`: `guestDeviceId`, `isGuest`. Условие `isLoggedIn()` не меняется (токен есть и у гостя).
- Подсказки зарегистрироваться (не блокируют работу):
  1. Профиль → «Аккаунт» у гостя: вместо email/пароля карточка «Вы в гостевом режиме: данные только на
     этом телефоне. Создайте аккаунт, чтобы не потерять их и открыть веб-версию» → Register (в режиме claim).
  2. Один раз, после 3-го записанного действия: bottom sheet с тем же текстом.
  3. «Купить» на пейволле → сначала регистрация, потом оплата.
- «Выйти» у гостя заменяется на «Удалить гостевые данные» с предупреждением: иначе выход = потеря.
- `RegisterScreen` в режиме claim вызывает `/auth/guest/claim` вместо `/register`.

### Веб
- На экране логина главная кнопка **«Попробовать без регистрации»**. Логика та же, `device_id` в
  `localStorage`. Блог → `/app/` → два тапа до «Сегодня».
- Те же подсказки (1) и (3). Карточка «Аккаунт» такая же, как на Android.

### Проверка
- vitest: `/auth/guest` идемпотентен; claim сохраняет `user.id` и данные; claim на занятый email → 409;
  гость → 403 на оплату/промокод; `/me` гостя; джобы писем не выбирают гостей.
- Руками (Android + веб): свежая установка → гость → участок → посадка → действие → claim →
  выход → вход по email → данные на месте.

### Риски
- Переустановка приложения теряет гостя (новый `device_id`). Лечится только подсказками (1)–(2).
- В БД копятся брошенные гости. Чистку (гости без активности > 180 дн.) — отдельной задачей, когда будет видно объём.
- Политика конфиденциальности: добавить абзац про анонимный идентификатор устройства.

## Вопросы к владельцу
1. **Гость — полный функционал** (всё, кроме оплаты и промокода), или регистрацию требовать при первой
   записи, как сказано в стратегии? Предлагаю полный: с серверным гостем принудительная регистрация ничего не даёт
   технически, а просить её лучше после первой пользы.
2. **Claim на уже занятый email** (у человека был аккаунт): предлагаю «Войти в существующий аккаунт,
   гостевые данные будут удалены» с явным предупреждением. Слияние двух аккаунтов не делаем.
3. **Веб-гость** — делаем в этом же релизе? Предлагаю да: это главный выигрыш от ссылок из блога.
4. **Контент 2.3** — пишу я, вы вычитываете? Или у вас есть свой список сезонных работ?
