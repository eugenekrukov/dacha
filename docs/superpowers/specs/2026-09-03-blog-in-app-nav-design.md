# Блог в приложении + раздел «Справочник» — Design Spec

**Дата:** 2026-09-03
**Исследование:** `docs/ui-navigation-research-2026-09.md` (вариант B принят владельцем 2026-09-03;
статья открывается на сайте, нативного рендера тела статьи не делаем).

## 1. Цель

1. Блог, который уже живёт на `calendacha.ru/blog/`, становится виден из приложения (web + Android):
   список статей внутри приложения и «Статья дня» на экране «Сегодня».
2. Меню перестаёт быть свалкой: таб «Ещё» превращается в **«Справочник»** (всё общее),
   личное и служебное уезжает в **«Профиль»** (всё моё). Число табов не меняется — 5.

## 2. Не цель (осознанно вне объёма)

- Нативный рендер тела статьи, WebView-экран, офлайн-кэш статей.
- Таблица постов в БД, админка, комментарии, лайки, подписка на теги.
- Глобальный поиск в шапке по всему приложению (вариант C исследования) — в `ux-roadmap.md`.
- Гейт по подписке на блоге: статьи бесплатны для всех, как и остальной `GET`-контент.

## 3. Целевая информационная архитектура

```
Нижняя навигация:  Сегодня · Календарь · Посадки · Справочник · Профиль

Справочник (общее для всех)          Профиль (моё)
├─ поиск: одно поле над всем         ├─ Лента участка
├─ [Все][Культуры][Болезни][Статьи]  ├─ Статистика и урожай
├─ Культуры        (67)              ├─ Журнал действий
├─ Болезни/дефициты (104)            ├─ Мои семена        ← из «Ещё»
└─ Статьи          (~73)             ├─ Аккаунт · Участок
                                     ├─ Настройки          ← из «Ещё»
                                     └─ Веб-версия (Android) ← из «Ещё»
```

**Поведение поиска** (ключевое изменение, чинит П3 исследования):

- пустой запрос → показывается список активного сегмента; сегмент «Все» при пустом запросе
  показывает статьи (самое свежее содержимое раздела);
- непустой запрос → ищем **по всем трём корпусам сразу**, результаты выводятся группами
  с заголовками «Культуры» / «Болезни и вредители» / «Статьи»; сегмент работает как фильтр группы;
- сопоставление — подстрока без учёта регистра по названию культуры / названию и синонимам
  записи справочника / заголовку статьи. Всё клиентское: три списка и так грузятся целиком
  (67 + 104 + страница фида), отдельный search-эндпоинт не нужен.

**Контекстные входы не трогаем.** Экраны `crops`/`crop_detail`/`guide`/`guide_detail` остаются
самостоятельными маршрутами: с них работает выбор культуры при создании посадки
(`Screen.Crops` из «Посадок», `CropDetail.showPlantButton`) и переход «Болезни/Вредители» из
карточки посадки (`Guide.withCrop`). «Справочник» переиспользует те же списковые компоненты,
а не подменяет маршруты.

## 4. Данные: `GET /blog/feed`

Блог — статика (`backend/scripts/generate-blog.js` → `landing/blog/**`, состояние в
`backend/scripts/.blog-manifest.json`, исходники — `docs/vk-content/*.md`). Ни таблицы, ни БД
не заводим: **новый роут читает те же файлы, что уже лежат на VPS рядом с бэкендом**
(`/var/www/dacha-api`).

```
GET /blog/feed?limit=20&offset=0     // публичный, без авторизации, без гейта
200 {
  items: [{
    slug: "chem-podkormit-tomaty-v-iyule",
    title: "Чем подкормить томаты в июле",
    url: "https://calendacha.ru/blog/chem-podkormit-tomaty-v-iyule/",
    published_at: "2026-07-04T10:00:00+03:00",
    image: "https://images.pexels.com/…" | null,
    lead: "Первый абзац статьи, до 200 символов…"
  }],
  total: 73
}
```

- Реализация — `backend/src/services/blogFeed.js`: читает манифест, группирует записи по
  `sourceFile`, парсит соответствующие `docs/vk-content/*.md` уже существующим
  `parseContentFile` (`src/services/vkContent.js`), сопоставляет по `title`, берёт первый абзац
  тела как `lead` (снять `#`/`**`, обрезать по 200 символов на границе слова).
- **Кэш в памяти**, инвалидация по `mtimeMs` манифеста (`fs.statSync` на запрос — дешевле и
  честнее TTL: перегенерация блога сразу видна).
- Манифеста нет (локальная разработка, свежий клон) → `{ items: [], total: 0 }`, не 500.
  Пути переопределяются env `BLOG_MANIFEST_PATH` / `BLOG_CONTENT_DIR` — так тесты подставляют
  фикстуры.
- Сортировка — `scheduledAt` по убыванию, при равенстве — по `slug` (детерминированность нужна
  «Статье дня», см. §6).
- Статьи с датой в будущем (файл контент-плана содержит и незапланированные ещё посты) в фид
  **не попадают** — манифест содержит только опубликованные, но проверку `scheduledAt <= now`
  ставим явно: генератор публикует весь файл целиком, включая посты «на завтра».

## 5. Экран «Справочник»

### Web

- Маршрут `/reference`, сегмент в query (`/reference?tab=articles`) — чтобы «назад» из статьи
  и шаринг ссылки внутри приложения возвращали в тот же сегмент.
- `components/Layout.tsx`: `PRIMARY` = Сегодня · Календарь · Посадки · **Справочник** · Профиль;
  массив `MORE` и компонент `MoreMenu` **удаляются целиком** (вместе с drop-up на мобильном).
- Новый `screens/ReferenceScreen.tsx`: поле поиска + чипы сегментов + рендер списков.
  Списки культур и проблем выносятся из `CropsScreen.tsx` / `GuideScreen.tsx` в
  `components/CropList.tsx` / `components/ProblemList.tsx` (последний уже существует — проверить,
  что переиспользуем его, а не пишем второй) и используются обоими экранами.
- Новый `components/ArticleList.tsx` — карточка: картинка (или эмодзи-заглушка 🌱, как в
  `renderCardMedia` генератора), заголовок, дата, лид в 2 строки. Тап → `window.open(url, '_blank',
  'noopener')`. Подгрузка следующей страницы кнопкой «Показать ещё» (не бесконечный скролл).
- `/crops` и `/guide` остаются рабочими маршрутами (контекстные входы, старые ссылки).

### Android

- `bottomNavItems`: `Screen.More` → `Screen.Reference` («Справочник», икона `Icons.Default.MenuBook`).
  `Screen.More` и `ui/more/MoreScreen.kt` удаляются.
- Новый `ui/reference/ReferenceScreen.kt` + `ReferenceViewModel` — поле поиска, `SegmentedButton`,
  списки. Списковые части `CropsScreen.kt` и `GuideScreen.kt` выносятся в переиспользуемые
  composable'ы (`CropListBody`, `GuideListBody`), сами экраны остаются как обёртки для
  контекстных входов.
- `ui/reference/ArticleListBody.kt` — карточка статьи (Coil для картинки, как в остальных списках).
  Тап → `CustomTabsIntent.Builder().build().launchUrl(context, Uri.parse(url))` — тот же приём,
  что уже используется в `ui/paywall/PaywallScreen.kt` (зависимость `androidx.browser` в проекте
  есть, новых не добавляем).
- Карточки «Мои семена», «Настройки», «Веб-версия» из `MoreScreen` переезжают в
  `ui/profile/ProfileScreen.kt` (тот же `HubCard`-паттерн, что у «Статистики» и «Журнала»).

## 6. «Статья дня» на экране «Сегодня»

- Размещение: **последняя секция экрана**, после «Советов дня». Верх экрана принадлежит задачам —
  см. `ux-roadmap.md`, «тревожная перегрузка задач» (закрыто 2026-08-08).
- Вид: одна карточка — маленькая картинка слева, заголовок + лид (2 строки) справа, подпись-ссылка
  «Читать статью →». Заголовок секции — «Почитать».
- Выбор статьи — чистая функция, одинаковая на обеих платформах, без состояния на сервере:

```
pickArticleOfDay(items, today):            # items отсортированы по дате ↓ (см. §4)
    pool = items с месяцем публикации == месяц(today)    # контент сезонный
    if pool пуст: pool = items
    if pool пуст: return null              # секция не рисуется
    return pool[dayOfYear(today) % pool.size]
```

  Один и тот же день → одна и та же статья на web и Android и при перезаходе.
  Отметки «прочитано» нет (потребовала бы состояния на сервере) — сознательный размен.
- Загрузка: тот же `GET /blog/feed?limit=50`. Ошибка сети / пустой фид / офлайн-режим «Сегодня»
  (`TodayCache`) → секция просто не рисуется. Кэшировать фид в офлайн-хранилище не будем —
  статья всё равно открывается в браузере, офлайн она бесполезна.

## 7. Ops и окружение

- **Новых шагов деплоя нет:** роут читает файлы, которые уже создаёт существующая процедура
  «Блог» из `docs/DEPLOY.md`. Условие — `landing/blog` и манифест генерируются в
  `/var/www/dacha-api`, как сейчас.
- **CSP веб-приложения** (`web/index.html`): в `img-src` добавить `https://images.pexels.com`
  и `https://ir.ozone.ru` — только эти хосты встречаются в `Картинка:` контент-плана (проверено).
  Потолок известен: новый хост картинки в контенте = правка CSP; при третьем таком случае
  переходим на локальное зеркалирование картинок при генерации блога, а не на `img-src https:`.
- `connect-src` менять **не нужно**: фид отдаёт свой же бэкенд (`'self'` в проде, `/api`-прокси
  в деве), а не `calendacha.ru`.
- Ссылки на статьи ведут на `calendacha.ru` — трафик и цели Метрики остаются на сайте.

## 8. Крайние случаи

| Ситуация | Поведение |
|---|---|
| Манифеста нет (dev, свежий клон) | `GET /blog/feed` → пустой список; сегмент «Статьи» показывает «Статей пока нет»; «Статья дня» не рисуется |
| Статья без `Картинка:` | Заглушка 🌱 в списке; в «Статье дня» карточка без картинки |
| Заголовок статьи изменили в `.md` | Манифест матчит по `title` → появится новая запись с новым slug (поведение генератора, не меняем) |
| Пользователь без сети | Список статей — состояние ошибки со ссылкой «Повторить»; «Статья дня» скрыта |
| Тап по статье, браузера нет (редкость на Android) | `runCatching` вокруг `launchUrl`, тост «Не удалось открыть браузер» |

## 9. Тесты

- **Backend** (vitest, `npm test`): `blogFeed.test.js` — лид из первого абзаца и обрезка;
  сортировка по дате; отбрасывание постов с датой в будущем; отсутствующий манифест → пустой фид;
  пересчёт кэша при изменении `mtime`. Плюс роутный тест на `limit/offset` и `total`.
- **Web**: `npm run typecheck` + чистая функция `pickArticleOfDay` в `web/src/lib/articleOfDay.ts`
  (тест-раннера в проекте нет — держим функцию отдельным модулем, чтобы её можно было
  прогнать вручную и позже покрыть).
- **Android**: `ArticleOfDayTest.kt` (JUnit) на ту же функцию — одинаковый результат для
  одинаковой даты, месячный фильтр, пустой список → null.

## 10. Что осознанно упрощено

- Нет отдельного search-эндпоинта: три корпуса и так на клиенте.
- Нет пагинации «бесконечным скроллом» — кнопка «Показать ещё».
- Нет тегов/рубрик статей: `Теги:` в контент-плане предназначены для соцсетей, в приложении
  фильтр по ним никто не просил.
