# Инструментация воронки регистрация→оплата — Design

**Дата:** 2026-09-02
**Владелец:** пользователь (соло-разработчик)
**Статус:** утверждено, план — следующий шаг

## Проблема

Бизнес-статус на 2026-09-02: 71 реальный пользователь, 0 платящих. Регистрации выросли в 7 раз
в августе, конверсия в оплату не сдвинулась. Существующий `/statistic_funnel` (скилл) не может
ответить, где именно отваливаются пользователи — воронка обрывается на «1-я посадка» и сразу
прыгает к «оплатили», без промежуточных шагов о том, кто вообще увидел предложение оплатить.

## Что уже есть в БД (не используется в отчёте)

- **Начал оплату** — `POST /billing/create-payment` уже пишет строку в `payments` со
  статусом `pending` до перехода пользователя на страницу оплаты ЮKassa. Незавершённый
  `pending` (не перешедший в `succeeded`) = брошенная оплата. Это готовые данные, отчёт их
  просто не читает.
- **«Старт триала»** (текущий шаг воронки) — мёртвый: `trial_started_at` = `created_at`,
  ставится ВСЕМ при регистрации (миграция 014, изначально был реальный триал-гейт, потом
  продукт перешёл на free-tier с лимитом посадок без триала). В текущей модели этот шаг
  всегда ≈100% и ничего не показывает — убираем из воронки.

## Чего в БД нет

1. **Упёрся в лимит посадок.** Сервер уже возвращает 402 в шести местах (создание посадки
   сверх `FREE_PLANTING_LIMIT`, и пять мест с `isPlantingLocked` — правка/фото/урожай/
   напоминание уже заблокированной посадки), но никуда это не пишет.
2. **Открыл экран пейволла.** Чисто клиентское событие (просмотр `PaywallScreen`), сервер о
   нём не знает.

## Решение

### 1. Схема

Миграция (следующий свободный номер после 088, определяется при реализации — на момент
дизайна `crops.soil_tips` уже занял 088):

```sql
ALTER TABLE users ADD COLUMN IF NOT EXISTS limit_hit_at TIMESTAMPTZ;
ALTER TABLE users ADD COLUMN IF NOT EXISTS paywall_opened_at TIMESTAMPTZ;
```

Оба поля — таймстамп **первого** события, дальше не перезаписываются (тот же паттерн, что
`email_verified`/`trial_started_at`: булев/таймстамп-флаг на `users`, не отдельная таблица
событий — в проекте нет универсальной аналитики событий, заводить её ради двух точек
избыточно; если появится третье-четвёртое событие в будущем — тогда стоит пересмотреть на
таблицу `analytics_events`, не раньше).

### 2. «Упёрся в лимит» — сервер

Новый хелпер в `backend/src/utils/access.js`:

```js
/** Отмечает первый упор пользователя в free-лимит (для воронки регистрация→оплата). */
async function markLimitHit(db, userId) {
  await db.query('UPDATE users SET limit_hit_at = NOW() WHERE id = $1 AND limit_hit_at IS NULL', [userId])
}
```

Вызывается «под» существующим `isPlantingLocked` без изменения его сигнатуры/чистоты (он
остаётся синхронной функцией без побочных эффектов — так тестируется независимо). Проверено
по коду на момент дизайна (`grep -rn "isPlantingLocked(\|plan_limit_reached"
backend/src/routes`) — ровно 7 точек, где нужна одна добавленная строка
`await markLimitHit(db, request.user.userId)` перед `reply.code(402)`:

- `backend/src/routes/plantings.js:102` — создание сверх `FREE_PLANTING_LIMIT` (`plan_limit_reached`)
- `backend/src/routes/plantings.js:270` — `isPlantingLocked`
- `backend/src/routes/plantings.js:309` — `isPlantingLocked`
- `backend/src/routes/actions.js:37` — `isPlantingLocked`
- `backend/src/routes/harvests.js:43` — `isPlantingLocked`
- `backend/src/routes/photos.js:58` — `isPlantingLocked`
- `backend/src/routes/reminders.js:25` — `isPlantingLocked`

**НЕ трогать** `plantings.js:231` и `plantings.js:257` — там `isPlantingLocked` используется
только для проставления информационного поля `locked: true/false` в ответах GET (список/деталь
посадки), это не 402 и не попытка записи — пользователь просто просматривает уже существующую
посадку, засчитывать это как «упёрся в лимит» было бы неверно (переоценило бы шаг воронки).

Номера строк ориентировочные (актуальны на момент дизайна) — реализация ищет по факту через
тот же grep, а не по жёстким номерам, которые могли сместиться.

**Почему не централизовать в `isPlantingLocked` напрямую:** функция сейчас синхронная и без
доступа к БД, вызывается в проверках владения и используется в тестах как чистая функция
(`freeTierState`+`isPlantingLocked` тестируются без БД). Превращать её в асинхронную с
side-effect усложнило бы контракт ради экономии нескольких строк в вызывающих местах —
разумный размен, дублирование самого 402-чека здесь уже было в коде до этой задачи.

### 3. «Открыл paywall» — клиент

Новый роут `POST /analytics/paywall-opened` (новый файл `backend/src/routes/analytics.js`
или существующий подходящий, если найдётся при реализации):

```js
fastify.post('/paywall-opened', { onRequest: [fastify.authenticate] }, async (request, reply) => {
  await fastify.db.query(
    'UPDATE users SET paywall_opened_at = NOW() WHERE id = $1 AND paywall_opened_at IS NULL',
    [request.user.userId]
  )
  return reply.code(204).send()
})
```

Вызывается один раз при маунте экрана пейволла:
- **Web** (`web/src/screens/PaywallScreen.tsx`) — `useEffect(() => { api.markPaywallOpened().catch(() => {}) }, [])`
- **Android** (`android/.../ui/paywall/PaywallScreen.kt` / `PaywallViewModel.kt`) — вызов из
  `init`/`LaunchedEffect(Unit)` вьюмодели, тем же паттерном fire-and-forget, ошибка не
  блокирует показ экрана

Rate limit — как у остальных authenticated POST-роутов в проекте (посмотреть дефолт на
момент реализации, отдельного лимита эндпоинту не нужно: вызывается максимум раз за сессию
по факту идемпотентности на сервере).

### 4. «Начал оплату»

Код не меняется. В отчёте используется существующая `payments`:
`count(DISTINCT user_id) FROM payments WHERE status IN ('pending', 'succeeded')`.

### 5. Итоговая воронка (`.claude/skills/statistic_funnel/SKILL.md`)

Шаги (только `is_test = false`):

1. Регистрация — `users`
2. Email подтверждён — `email_verified`
3. Участок создан — `gardens`
4. 1-я посадка — `plantings`
5. **Упёрся в лимит** — `limit_hit_at IS NOT NULL` *(новое)*
6. **Paywall открыт** — `paywall_opened_at IS NOT NULL` *(новое)*
7. **Оплата начата** — `payments.status IN ('pending','succeeded')` *(новое использование
   существующих данных)*
8. Оплатили — `payments.status = 'succeeded'` (как сейчас)

Шаг «старт триала» убирается целиком (мёртвый, см. выше). SQL-запрос в скилле переписывается
под новый список шагов тем же способом (один `SELECT` с подзапросами, вывод конверсии между
соседними шагами в %).

## Что не входит в объём

- Не строим общую таблицу событий/аналитики — сознательно, см. п.1
- Не логируем повторные визиты на paywall/повторные упоры в лимит (только факт первого раза)
- Не добавляем client-side событие «нажал кнопку оплаты» отдельно от «оплата начата» —
  `payments.status='pending'` уже эквивалентен этому клику (создаётся в момент нажатия)
- Не трогаем сами 402-ответы и их коды/сообщения — только дописываем маркер рядом
- Не делаем разбивку воронки по каналу/когорте/дате — только суммарные числа, как в текущем
  `/statistic_funnel`

## Тестирование

- Backend: юнит-тест на `markLimitHit` (первый вызов ставит `limit_hit_at`, повторный не
  перезаписывает) — по образцу существующих тестов `access.js`, если есть, иначе новый файл
  `__tests__/unit/access.test.js`
- Backend: тест на `POST /analytics/paywall-opened` — ставит `paywall_opened_at` один раз,
  идемпотентен, 401 без токена
- Регрессия: `npm test` — существующие тесты на 402 в `plantings.js`/`actions.js`/
  `harvests.js`/`photos.js`/`reminders.js` не должны сломаться (маркер не меняет статус/тело
  ответа)
- Web/Android: ручная проверка (нет раннера) — открыть `PaywallScreen`, убедиться в вызове
  `/analytics/paywall-opened` (network-таб / логи), повторное открытие не дублирует (сервер
  идемпотентен, дублирующий запрос безвреден)
