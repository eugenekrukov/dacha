# Площадь грядок + советы по типу почвы

## Контекст

`docs/ux-roadmap.md` §5.1 держал пункт «поля площадь/тип почвы» под открытым вопросом
владельца (2026-06-25): метаданные без функциональной привязки, не строить, пока не
найдена конкретная польза. Пользу нашли (2026-09-02) — см. ниже. `gardens.area_m2`
(площадь всего участка) при этом остаётся неиспользуемой и исключена из задачи: расчёт
вместимости уже закрыт на уровне отдельных грядок (`garden_beds.width_cm/length_cm`,
миграции 070/071, фича «Схема посадки культур + размеры грядки», `docs/ux-roadmap.md`
раздел «Сводка открытого», реализовано 2026-08-14).

Задача распадается на два независимых куска.

## A. «Общая площадь грядок»

**Проблема:** размер грядки (`width_cm`/`length_cm`) вводится пользователем на уровне
отдельной грядки (подсказка вместимости — `BedField.tsx`/`BedPickerField.kt`), но нигде
не суммируется в площадь всего участка.

**Механизм редактирования уже существует** — проверено (2026-09-02):
- Backend: `PATCH /beds/:id` (`backend/src/routes/beds.js`) уже принимает `width_cm`/`length_cm`
  для существующей грядки, `null` явно снимает размер.
- Web: `BedField.tsx` — инлайн-переименование+правка размера у уже созданной грядки
  (`submitRename`/`renameWidth`/`renameLength`).
- Android: `BedPickerField.kt` — паритетный `onRename(bed, name, widthCm, lengthCm)`.

Значит новых эндпоинтов/новой инфраструктуры редактирования не требуется — только чтение
и суммирование уже существующих данных.

**Дизайн:**
- Сумма `Σ (width_cm × length_cm) / 10000` (м²) по грядкам сада, где **оба** поля заполнены.
  Грядки без размера в сумму не входят.
- Отдельная строка-подсказка под суммой: «N грядок без размера — укажите» — если есть
  грядки, у которых `width_cm`/`length_cm` не заполнены (или заполнено только одно из двух).
  Подсказка ведёт к тому же пикеру грядок, где размер уже можно вписать (см. выше — правка
  готова, дополнительный UI не нужен).
- **Место показа:** шапка вкладки «Мой участок» (`ProfileScreen`/аналог на Android) — там уже
  частично живёт §5.2 «профиль участка» (шапка вкладки, реализовано 2026-06-22), расширяем
  существующий блок, не создаём новый экран.
- **Backend:** новый роут не нужен — расчёт чистой функцией на клиенте из уже отдаваемого
  `GET /beds` (список грядок сада с размерами уже приходит целиком).

## B. Советы по типу почвы

**Проблема:** `gardens.soil_type` (миграция 001, комментарий-заготовка `loam | sandy | clay |
peat | black_earth`) принимается роутами `POST/PUT /gardens` уже с самого начала, но:
- **UI для выбора отсутствует на обеих платформах** — на web поля нет вообще ни в одной форме
  участка; на Android поле `soilType` есть только в модели данных (`Models.kt`,
  `GardenRepository.kt`), в `GardenEditScreen.kt` инпута нет. Пользователь физически не может
  это значение задать.
- Значение нигде не читается в логике (только пишется/читается назад тем же роутом).

**Найденная польза (владелец, 2026-09-02):** тип почвы должен давать регулярные советы по
улучшению почвы и влиять на подачу советов по поливу/подкормке/уходу — растения по-разному
ведут себя на разных почвах, это должно быть отражено в советах.

### Типы почвы

Берём готовую заготовку без изменений: `loam` (суглинок) · `sandy` (песчаная) · `clay`
(глинистая) · `peat` (торфяная) · `black_earth` (чернозём). RU-подписи для UI — этими же
словами.

### Данные

Новая колонка `crops.soil_tips` JSONB — по образцу уже существующих культуро-специфичных
JSONB-полей (`watering_details`, `fertilizing_schedule`, `diseases`, `pests` и т.д., не
отдельная join-таблица):

```json
{
  "loam": "текст: полив/подкормка/уход/улучшение почвы для этой культуры на суглинке",
  "sandy": "...",
  "clay": "...",
  "peat": "...",
  "black_earth": "..."
}
```

Одна строка на культуру (67 строк), а не join-таблица «культура × почва» (335 строк) —
меньше миграционной/DML-возни при том же покрытии.

### Логика показа

Расширяется существующий механизм культуро-специфичных советов дня (`getCropStageTip`,
фича «Советы дня стали культуро-специфичными», 2026-07-30): при выборе совета для карточки
культуры на «Сегодня» —
- если у сада заполнен `soil_type` **и** у культуры есть непустой `soil_tips[soil_type]` —
  подмешивается к совету по стадии (агрономия по стадии остаётся основой, почвенное
  примечание — дополнение, не замена);
- если `soil_type` не заполнен (подавляющее большинство существующих участков сегодня) или
  для культуры нет текста под этот тип почвы — откат к текущему поведению без всяких
  изменений (совет по стадии/общий пул, как сейчас). Пустых мест в советах быть не должно.

### UI ввода

Пикер типа почвы (5 вариантов) добавляется в форму создания/правки участка:
- Web — форма участка (сейчас без этого поля вовсе).
- Android — `GardenEditScreen.kt` (модель поле `soilType` уже готово, не хватает только инпута).

### Контент — отдельный этап, не в этой задаче

67 культур × 5 типов почвы — предметное исследование (агрономия), а не код. Пишется
батчами с проверкой минимум по 2 источникам на каждую запись — так же, как уже делали
справочник болезней/вредителей (миграции 081/082) и сроки урожая у сортов
(`docs/superpowers/plans/2026-08-17-crop-varieties.md`). План реализации покрывает только
механизм: колонку, откат при отсутствии значения, подмешивание в совет дня, UI выбора
почвы. `soil_tips` едет в проде пустой (`{}` у всех 67 культур) — контент заполняется
отдельными сессиями после того, как сам механизм в проде и подтверждён.
