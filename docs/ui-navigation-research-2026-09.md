# UI-исследование: навигация и место для блога (2026-09-03)

> Повод: в приложении (веб + Android) нет блога, который уже есть на сайте (`/blog/`, до 73 статей
> из `docs/vk-content/*.md`). Добавить его «ещё одним пунктом» некуда — меню уже воспринимается
> как перегруженное, часть разделов пользователь не находит.
> Задача этого документа — не «куда воткнуть блог», а **на какой каркас навигации его класть**,
> чтобы следующие 2–3 новых раздела тоже легли без ломки.

## 1. Что есть сейчас (инвентарь, обе платформы)

Навигация уже зеркальна: web `components/Layout.tsx` (`PRIMARY` + `MORE`) ↔ Android
`navigation/Navigation.kt` (`bottomNavItems`) + `ui/more/MoreScreen.kt`.

| Слой | Web | Android |
|---|---|---|
| Нижний бар / чипы в шапке | Сегодня · Календарь · Посадки · Профиль · **Ещё** | то же, 5 табов |
| «Ещё» | Мои семена · Справочник культур · Болезни и дефициты · Настройки | + Веб-версия (5 карточек) |
| «Профиль» (хаб) | Лента участка · Статистика и урожай (`/harvests`) · Журнал действий (`/journal`) · Аккаунт · Участок | то же |
| Без пункта меню вовсе | `/crops/:id`, `/guide/:slug`, `/paywall`, `/garden/edit`, `/plantings/:id` | те же + `Analytics`, `Harvest` |

Глубина доступа (мобильный веб / Android, от «Сегодня»):

- «Болезни и дефициты» — 2 тапа (Ещё → пункт);
- карточка культуры — 3–4 (Ещё → Справочник культур → поиск → карточка);
- «Журнал действий» — 2 (Профиль → Журнал);
- «Мои семена» — 2 (Ещё → пункт).

**Глубина — не проблема.** Всё в 2–4 тапах. Проблема в другом.

## 2. Диагноз

**П1. Два из пяти табов не называют своё содержимое.**
«Ещё» — по определению ни о чём. «Профиль» человек читает как «мои данные/аккаунт», а внутри —
лента участка, статистика урожая и журнал действий, то есть половина истории его сезона.
Пользователь не ищет журнал в «Профиле», потому что журнал — не профиль.

**П2. «Ещё» — смешанный ящик, а не раздел.** Внутри одновременно: справочная информация
(культуры, болезни), личный инвентарь (семена), системные настройки и внешняя ссылка на
веб-версию. Общего признака нет → нет и правила, по которому пользователь догадается,
что искать надо там. Добавление блога делает ящик на один разнородный пункт хуже.

**П3. Поиск раздроблен по экранам.** Поиск по культурам живёт в `CropsScreen`, поиск по проблемам —
в `GuideScreen` (`web/src/screens/*`, на Android аналогично). Это два независимых поля над одним
по сути корпусом справочной информации: 67 культур + 104 записи о болезнях/вредителях, а с блогом
станет ещё +до 73 статей. **Свыше 240 единиц контента без единой точки поиска** — вот настоящая
причина ощущения «непонятно, где искать».

**П4. Прочитать нечего, кроме справочника.** Контент-машина проекта (ВК / Telegram / Дзен / сайт)
приложению не видна вообще. Единственный «читательский» контент внутри — карточки культур и
болезней, то есть только справка «по запросу», без регулярного повода зайти. Блог здесь не
украшение, а недостающий повод открыть приложение в день, когда на грядке дел нет.

**П5. Бэклог упирается в ту же стену.** В `docs/ux-roadmap.md` открыты «перечень посадок по грядке»
и «фильтр журнала + правка записи» — оба тоже не имеют очевидного места. Значит, каркас нужно
чинить сейчас, до блога, иначе каждый следующий раздел будет отдельным спором.

## 3. Варианты

### A. Минимальный: «Блог» шестым пунктом в «Ещё»

Одна строка в `MORE` и одна карточка в `MoreScreen`. Плюсы: 20 минут работы, ничего не ломается.
Минусы: усиливает П1–П3, блог оказывается в самом невидимом месте приложения. Для контента,
который должен возвращать пользователя, — худшее из возможных мест.

### B. Рекомендуемый: переименовать ящики по содержимому — «моё» vs «общее»

Правило, которое пользователю можно объяснить одной фразой: **общее для всех — в «Справочнике»,
моё личное — в «Профиле»**.

```
Нижняя навигация (5 пунктов, было 5):
  Сегодня · Календарь · Посадки · Справочник · Профиль
                                   ^^^^^^^^^^   ^^^^^^^
                                   бывш. «Ещё»  + вернувшиеся сюда разделы

Справочник (общее):     [Культуры] [Болезни] [Статьи]  + ОДНО поле поиска над всеми тремя
Профиль (моё):          Лента · Статистика и урожай · Журнал · Мои семена ·
                        Аккаунт · Участок · Настройки · Веб-версия
```

Что меняется по факту:
- таб «Ещё» исчезает как понятие — становится «Справочником» с сегментами;
- «Мои семена», «Настройки», «Веб-версия» уезжают в «Профиль» (это личное/служебное, не справка);
- поиск в `CropsScreen` и `GuideScreen` схлопывается в один над сегментами — по культурам,
  проблемам и заголовкам статей сразу;
- блог получает не строчку в меню, а треть раздела, который прямо называется тем, что внутри.

Цена: число пунктов нижней навигации не растёт, но два экрана (`MoreScreen` / `MORE`-меню)
переписываются в один сегментированный, а `Профиль`-хаб получает 3 новые карточки.
Все затронутые экраны уже существуют — новых сущностей, кроме списка статей, не появляется.

### C. Максимальный: глобальный поиск в шапке + B

Поверх B — поле поиска в шапке на всех экранах, ищущее по культурам, проблемам, статьям и
**своим посадкам**. Это правильный конечный вид, но это отдельная фича со своим бэкендом
(единый search-эндпоинт) и своим экраном результатов. Не в этот заход: в B поиск уже становится
единым внутри «Справочника», а это 90% пользы за 20% работы.

**Вывод: делаем B.** A — отвергнут (закрепляет проблему), C — записать в `ux-roadmap.md`
как следующий шаг, если по метрикам поиск внутри «Справочника» будет использоваться.

## 4. Как в каркас B ложится блог

**4.1. Раздел «Статьи»** — третий сегмент «Справочника»: лента карточек (картинка, заголовок,
дата), пагинация/подгрузка, работает тот же общий поиск.

**4.2. «Статья дня» на «Сегодня»** — одна карточка в самом низу экрана, после «Советов дня»
(зона «дел уже нет, есть что почитать»), а не сверху: верх экрана принадлежит задачам, и
разбавлять его контентом нельзя — это ровно то, от чего лечили «тревожную перегрузку задач»
(см. `ux-roadmap.md`, закрыто 2026-08-08).

Выбор статьи — детерминированный, без состояния на сервере: из статей, опубликованных в **том же
месяце** (любого года — контент сезонный), берётся `dayOfYear % n`; если таких нет — последняя.
Один и тот же день = одна и та же статья на обеих платформах и при перезаходе.

**4.3. Источник данных.** Блог сегодня — статика: `backend/scripts/generate-blog.js` рендерит
`landing/blog/**` из `docs/vk-content/*.md`, состояние — в `.blog-manifest.json`, ни таблицы,
ни API нет. Заводить таблицу и роут ради списка статей не нужно: генератор уже держит все нужные
поля в руках и может дописать рядом со страницами **один JSON-фид** (`landing/blog/feed.json`) —
`slug`, `title`, `scheduledAt`, `image`, `lead`. Клиенты читают его как обычную статику.
Ни миграции, ни новых роутов, ни второго источника правды.

## 5. Что сознательно не делаем

- **Не добавляем шестой таб.** Пять — потолок для нижней навигации, и он уже занят.
- **Не строим CMS/таблицу постов.** Контент-пайплайн (md → ВК/Telegram/Дзен/сайт) работает;
  приложение — ещё один потребитель того же файла, а не новый редакторский контур.
- **Не делаем комментарии, лайки, подписки на теги.** Нечего поддерживать при 0 платящих.
- **Не трогаем «Сегодня»/«Календарь»/«Посадки»** — ядро цикла, оно не сломано.

## 6. Что нужно решить владельцу (до спеки)

1. **Как читается статья**: открывать статью сайта во внешнем браузере / Custom Tab (ноль
   дублирования, статья всегда актуальна, работает уже существующий HTML с FAQ и CTA) —
   или рендерить нативно в приложении из того же фида (плавнее, но нужен полный текст в фиде
   и два рендерера, а CTA «открыть приложение» внутри приложения надо прятать).
2. **Принимается ли перестановка B** — то есть переезд «Мои семена», «Настройки» и «Веб-версии»
   из «Ещё» в «Профиль» и переименование таба в «Справочник».
