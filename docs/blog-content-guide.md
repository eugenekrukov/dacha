# Статьи для блога `/blog/` — как писать и публиковать

> С 2026-09 (стратегия `docs/strategy-2026-09.md`, автопостинг ВК/Telegram на паузе) блог на
> `calendacha.ru/blog/` — **основной канал контента**, а не побочный архив постов из соцсетей.
> Статья пишется сразу под поисковый запрос и под ответ ИИ-поиска, без адаптации под ленты.
> Файлы по-прежнему лежат в `docs/vk-content/batch-YYYY-MM-partN.md` (историческое имя папки,
> парсер общий с `vk-queue.js` — `src/services/vkContent.js`); генератор — `backend/scripts/generate-blog.js`.

## Формат поста в батч-файле

```
## 2026-09-22 10:00 — Когда выкапывать морковь осенью и как её хранить

Лид: 2–3 предложения — прямой ответ на запрос, самодостаточный.

### Подзаголовок-подзапрос
Текст…

FAQ:
В: Вопрос в формулировке реального запроса?
О: Ответ в 1–3 предложения, понятный без остального текста.

Картинка: https://images.pexels.com/…?auto=compress&cs=tinysrgb&w=1280
```

Секции `Telegram:`, `Теги:` и кросс-ссылки на соцсети — **не нужны** (каналы на паузе; блог их
не использует). Не добавлять в тело фразы вроде «подсказки — в Telegram-канале»: ссылки на
ВК/Дзен/Telegram из продукта убраны. CTA — только приложение и только на реальные функции.

## Правила

**Заголовок (`## дата — Заголовок`)**
- Это и есть поисковый запрос: «Когда выкапывать георгины осенью и как хранить клубни»,
  а не хук вроде «Георгин: почему клубни выкапывают только после заморозка».
- Главное слово — в начале и в первых 60 символах: **слаг URL = транслит заголовка, обрезанный
  до 60 символов, и после публикации не меняется** (страница уже в индексе). Заголовок продумать
  до первой публикации — переименование = новый URL и потеря старого.
- До ~60 символов вместе с ` | Календарь дачника` — иначе бренд в `<title>` отбрасывается.
- Секция `SEO:` больше не нужна — задавать запрос прямо в заголовке. Остаётся поддержанной
  только для старых постов, где заголовок-хук уже стал слагом.

**Дата.** Дата и время в заголовке — момент выхода статьи: они становятся `datePublished`.
Батч выходит по таймеру, по одной статье в день в `00:00` (МСК): ставить `## 2026-09-22 00:00 — …`,
следующую на следующий день. Публикует cron на VPS (см. «Публикация по таймеру»). Без флага `--due`
`generate-blog.js` публикует весь файл сразу, поэтому вручную запланированный батч без него не гонять.

**Длина и структура**
- Ориентир 6000–9000 знаков (раньше 3000–4000 под ленту). Длина — не самоцель: каждый раздел
  отвечает на отдельный связанный запрос («когда», «как», «чем опасно», «что делать, если…»).
- **Первый абзац** уходит в `<meta description>` (обрезается до 155 знаков) и в
  `speakable` — он должен быть законченным ответом на запрос, без «в этой статье мы…».
- Подзаголовки — только `###` (в HTML все становятся `<h2>`, вложенных уровней нет). Формулировать
  как вопрос или запрос: «Как хранить клубни зимой», а не «Хранение».
- Разметка тела: абзацы и `**жирный**`. `- ` списки рендерятся строками через `<br>`, а не `<ul>`;
  таблиц нет. Если нужен настоящий список или таблица — сначала доработать `mdBodyToSections`
  в `generate-blog.js`.
- Факты — конкретные (сроки, температуры, размеры, числа), без «как правило» и общих слов.

**FAQ (`FAQ:`) — обязателен, 3–5 пар.** Вопросы — как их вводят в поиск («Можно ли…», «Через
сколько…»), не пересказ подзаголовков. Ответ — 1–3 предложения, понятных без чтения статьи
(их цитируют ИИ-ответы и расширенный сниппет). Пары отделяются пустой строкой.

**Картинка (`Картинка:`) — обязательна**: идёт в `og:image`, карточку блога и `image` в разметке.
Проверять, что на фото именно та культура (были случаи: тыква вместо патиссона).

**Темы и CTA**
- Тему сверять с `GET https://calendacha.ru/crops` ДО написания: CTA «сроки для вашей культуры
  в приложении» — враньё, если культуры нет в справочнике.
- Не заканчивать статью отдельной строкой-рекламой вида «Сроки для X — в приложении «Календарь
  дачника»»: блог живёт на сайте самого приложения, а под статьёй генератор уже ставит кнопку
  «Открыть «Календарь дачника» →» на `/app/`. Упоминать приложение можно только внутри текста, по делу
  (конкретная функция под конкретную проблему). Такие хвосты убраны из батчей 2026-09 part1–3 (2026-09-22).
- Тему сверять со ВСЕМИ прошлыми `docs/vk-content/batch-*.md` (в т.ч. по манифесту
  `backend/scripts/.blog-manifest.json`), не только с последними — дубли уже случались.
- Не создавать две статьи под один запрос; если тема уже есть — обновлять существующую.

**Стиль:** `editor-ru → redaktura → humanizer-ru → proofreader-ru`.

## Schema.org и мета — генерируются автоматически

Руками разметку не писать. `generate-blog.js` собирает для каждой статьи:
- `BlogPosting` (headline, description, datePublished, image, author, `speakable` по `h1` и `.lead`);
- `BreadcrumbList` (Главная → Блог → статья);
- `FAQPage` из секции `FAQ:` — и тот же текст виден на странице (`<details>`), как требует Яндекс/Google;
- `title`, `description`, canonical, Open Graph, запись в `sitemap.xml`.

Известное ограничение: `dateModified` = `datePublished` (даты правок не хранятся). Дату в
заголовке при переработке старой статьи менять можно (слаг от даты не зависит), но тогда
изменится и `datePublished` — решать осознанно.

## Публикация по таймеру (основной способ)

Новый батч: файл `docs/vk-content/…md` с датами по одной статье в день (`00:00`) → коммит в `main`
→ доставка на VPS (см. ⚠️ ниже про ветку). Дальше всё делает cron на VPS:

```
0 21 * * * sh /var/www/dacha-api/backend/scripts/publish-blog-due.sh
```

Сервер в UTC, поэтому `21:00` UTC = `00:00` МСК. Скрипт берёт два последних `batch-*.md`, запускает
`generate-blog.js --due` (публикует только новые статьи, чей `scheduledAt` наступил), синхронизирует
`landing/blog` и `sitemap.xml` в `/var/www/dacha-landing/` и шлёт в IndexNow только новые URL.
Лог — `/var/log/dacha-blog-publish.log`. Следующий батч подхватится сам, ставить cron заново не нужно.
Проверка «что уже вышло»: `backend/scripts/.blog-manifest.json` на VPS.

## Публикация вручную (всё сразу)

Файл `docs/vk-content/…md` → коммит → доставка на VPS → генерация → копирование → IndexNow:

```powershell
ssh hetzner 'cd /var/www/dacha-api && git branch --show-current && git log -1 --oneline'
ssh hetzner 'cd /var/www/dacha-api/backend && node scripts/generate-blog.js ../docs/vk-content/<файл>.md'
ssh hetzner 'rm -rf /var/www/dacha-landing/blog && cp -r /var/www/dacha-api/landing/blog /var/www/dacha-landing/blog && cp /var/www/dacha-api/landing/sitemap.xml /var/www/dacha-landing/sitemap.xml'
ssh hetzner 'cd /var/www/dacha-api/backend && node scripts/submit-indexnow.js'
```

⚠️ **Проверить ветку на VPS перед `git pull`.** На 2026-09-17 прод жил на
`feature/garden-area-soil-tips` (на 66 коммитов впереди своего origin), а не на `main`
(`main` там отставал на 84 коммита). Простой `git pull` ничего не доставлял. Контент-коммит
из `main` брался через `git fetch origin && git cherry-pick <sha>`, без merge/reset.

Обновить уже опубликованные страницы (новая обёртка, добавленные FAQ) без публикации новых:
`node scripts/generate-blog.js ../docs/vk-content/<файл>.md --refresh-existing`.

После публикации проверить на живой странице: заголовок, блок «Частые вопросы», картинку и
что статья есть в `https://calendacha.ru/sitemap.xml`. Приложение подхватит статью само
(`GET /blog/feed` читает тот же манифест).
